# fw/ — the tracker firmware, on Dinghy

Copied from [zvenson/dinghy](https://github.com/zvenson/dinghy) at `929730019a9dc362c12a710c0b139cbfefb582e9`
(2026-10-09, Dinghy 0.1; reference clone in `third_party/dinghy`), as its MAKE-IT-YOURS.md suggests. Changes:

- `firmware/src/dinghy.c` replaced by `firmware/src/tracker.c` (the app); `tools/build.py` compiles it.
- `firmware/gen/font_6x12.h`: Spleen 6x12 (BSD-2), from `python -I tools/bdf2c.py fw/firmware/gen/font_6x12.h FONT6X12 third_party/fonts/spleen-6x12.bdf`.
- `firmware/sound/`: **Felucca's sound layer**, copied unchanged from [hugelton/Felucca](https://github.com/hugelton/Felucca)
  at `ac6bfcbd76ee3de79eb461719e8d123b5512aa3c` (v1.1.5.1, `third_party/felucca`): `core.h`, `engines.c`, `dsp.c`, every
  `eng_*.c`, `fm6_core.c` (msfa, Apache-2.0), `phys_dsp.c` / `phys_symp.c` (DaisySP, MIT), `drum_voice.c`, `fm4_convert.c`,
  `params.c`, `mod.c`, `voice.c`, `slicer.c`, `fx.c`, `perform.c`, `click.c`. Each file keeps its own licence header.
  `firmware/src/sound.c` includes them in Felucca's order and supplies what Felucca's UI and sequencer otherwise
  would (a sound load: `ui.c` set_engine_of / apply_preset_to without undo; the power-on defaults of `main.c`).
  The tracker's player is `events_block()` (Felucca's sequencer hook, called by `fx.c mix_block`).
- `firmware/gen/felucca_tables.h`, `felucca_fm6.h`, `felucca_samples.h`: generated by Felucca's own tools
  (`python -I third_party/felucca/tools/gen_tables.py fw/firmware/gen/felucca_tables.h`, likewise `gen_fm6_patches.py`
  and `gen_samples.py`).
- **The store** (2026-10-10, the tracker's saving; `docs/flash-map.md`): `firmware/src/platform.c` has
  `store_read` / `store_erase` / `store_write` over the data region `0x97000–0xDFFFF` and lets `FL_RANGE_OK` write
  there; `tests/host.c` and `web/dinghy-emu/dinghy_wasm.c` (the emulator, which also keeps it in the page) have the
  same calls over a RAM image; `fw/docs/API.md` "Store". `firmware/loader/ldr_core.c` skips that region when it
  clears update records, as Felucca's loader does (Dinghy's did not: a project sector could have been erased).
- **The device build on Windows** (2026-10-10, step 19): `tools/build.py` passes paths to the Docker container in
  POSIX form and puts `firmware/sound` on the app's include path; `firmware/src/sound.c` renames the boot guard that
  ends Felucca's `core.h` (Felucca's `main.c` one, unused here; it clashed with Dinghy's `bootguard.h`) instead of
  editing Felucca's file.
- `firmware/src/libc.c` `fmt_fix` (2026-10-10, the X page): a value under 1 kept no 0 before the point (`.5`,
  `.0`); it writes `0.5`, `0.0` now (every caller: dB levels, Hz, ms).
- **Host mode for the tracker** (2026-10-11): `tests/run_host.sh` builds `tracker.c` (any host compiler, `CC`; on Windows the
  project's zig) and plays `tests/host_phrase.txt` (a 4-note phrase written and played with the gamepad keys) instead of
  `host.c`'s Dinghy script; it fails if the phrase is silent. `tests/host.c` includes `libc.c`'s helpers (its `memset` /
  `memcpy` / `memcmp` renamed, the host's are used) and the LED matrix `tracker.c` writes (`FM1_KEYMAP`, `fm1_led`,
  `fm1_led_dim`; never shown).
- **Two fixes from the FM-1 firmware survey** (2026-10-11, `docs/research/fm1-firmwares.md` §10): `firmware/hal/fm1_lcd_hw.h`
  `fm1_lcd_rail_on()` (PA2 low, split out of `fm1_lcd_hw_init`: it also powers the key matrix) called by
  `firmware/src/recovery.c recovery_key()` before its scan (that function went with the boot stub, below); `firmware/sound/drum_voice.c` `dv_rim_run` / `dv_bell_run`
  widen two products to int64 before the shift (as ELI7VH/Felucca; they wrapped at high TONE / SNAP / ACC), so that
  file is no longer Felucca's unchanged copy.
- `firmware/src/lcd.c` `LCD_BAUD` 4 → 0 (2026-10-12, `docs/ux/unit-feedback.md` #24 #38): SPI1 at 60 MHz (~44 MHz measured), as
  charlesvestal/fm1-ctl runs it on the device (its `lcd.c` is this one with that value). Only the app includes `lcd.c`;
  the stub and the loader keep their own screen code.
- **The boot stub** (2026-10-11, `docs/boot-stub-plan.md`): `firmware/stub/` copied unchanged from
  [Quixotic7/ChoralRootFM1](https://github.com/Quixotic7/ChoralRootFM1) at `a0dd291acd45` (stub version 3; its comments
  name ChoralRoot's paths: `docs/BOOT-SAFETY.md` is theirs). `app.ld` moves the app to `0x02001000` and NOINIT above the
  stub's RAM words, `crt0.S` no longer saves the SPL's state (the stub does), the app's OCT- rescue check
  (`recovery.c recovery_key`) is gone (the stub owns the gesture), `ota.c` keeps a staged loader of ours
  (`ota_staged`, `ota_boot_cleanup`), `loader/ldr_core.c` writes in the marker's order, `tools/fm1pkg_make.py` writes
  the marker and the compensation bytes, `tools/build.py` builds the stub and checks it against `stub.lock`. Tests:
  `tests/run_boot_tests.py` (`stub_test.c` from ChoralRoot's `cr_stub_test.c`, `ldr_test.c` from their `ldr_test.c`).
- Not copied: Dinghy's logo (designburg, not under the GPL) and its screenshot.
- Not done yet: our own package identity (`PRODUCT` in tools/build.py is still Dinghy's `FM-1_990`); no device build
  has been made. Nothing here is to be installed on the FM-1 without the user's go-ahead (CLAUDE.md).
- `firmware/sound/fx.c`: the `#include "perform.c"` line dropped; `slicer.c` and `perform.c` stay in the tree but are not compiled (stubs in `src/sound.c`, decisions.md 2026-10-12).
- `firmware/sound/eng_grain.c`: `GR_NIDX` 1024 → 512 and `GR_MAXZ` 32 → 16 (OPTIMIZE M4: the seek index was sized for the retired PERC set; pool −6.5 KB).

Run it in the browser: `python web/dinghy-emu/build.py --app fw/firmware/src/tracker.c --name KETCH --ver 0.1`,
then the `dinghy-emu` launch entry (http://127.0.0.1:8767, `?fw=tracker` is the default). Checks: `node fw/tests/tracker_emu.mjs`.
